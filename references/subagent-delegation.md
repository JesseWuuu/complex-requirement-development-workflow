# Sub Agent 派发与回收

本参考文件扩展父级 `SKILL.md` 的 Sub Agent 核心规则。任务包只服务当前运行过程；跨对话状态只保存绑定当前输入的有效结论，不保存调度历史。

## 收益门槛与数量

- 阶段 2、4、5 的调查以及阶段 7 的实施，只有可并行的独立技术面能明显节省时间时才派发；文档主笔、共享接缝、重叠写入和局部小修由主 Agent 完成。
- 阶段 2、4、5 同一时刻最多 2 个调查任务；阶段 7 同一时刻最多 2 个实施任务。不要为了用满并发而切分。
- 阶段 6 的独立文档审阅和阶段 7 的终结代码审阅是固定门槛，各自只允许一个当前 reviewer，不适用收益判断。
- 规划或实施任务失败后，主 Agent 收窄范围并接管；不要反复换 Agent。强制审阅没有完整结论时按“审阅恢复”处理。

## 按阶段切分

- **阶段 2：** 可拆分 Figma/设计事实、入口与导航、API/数据/状态、实验或测试基础设施等互不依赖的只读证据面。主 Agent 负责端到端语义和冲突裁决。
- **阶段 4：** 只派发现有逻辑风险或契约覆盖调查；`test.md` 由主 Agent 统一编写。
- **阶段 5：** 只派发实施目标、文件归属、新机制必要性或验证目标调查；`implementation.md` 由主 Agent 统一编写。
- **阶段 6：** 使用未参与文档主笔或关键技术结论的干净 Sub Agent，只读检查必要性、依据、跨文档一致性、可执行性和精简度。
- **阶段 7 实施：** 从已批准实施编排生成互不重叠的写入任务；主 Agent 可按核心 Skill 的变更分级补充运行时目标。共享模型、公共接缝和最终集成保留给主 Agent。
- **阶段 7 终结审阅：** 代码实施完成且验证结果已记录，实施结果为 `implemented` 或 `verified` 后，使用未参与本工作流规划、实施或阶段 6 审阅的全新 Sub Agent，只读审阅最终代码；失败或条件不足的验证项不阻止派发。

## 运行时任务包

每个任务包包含：

1. 当前阶段和单一、有边界的目标；
2. 准确的需求、文档、仓库根目录和适用规则；
3. 允许读取的范围；写入任务还要给出唯一写入范围和禁止目标；
4. 依赖、共享接缝与主 Agent 负责的集成点；
5. 精简返回格式：结论、证据、阻塞、受影响路径、验证和偏差。

实际 Agent ID、等待记录、修订次数和任务包清单只保留在当前对话上下文。只有结论会改变后续决策时，才把精简结论写入权威正式文档、`grounding-pack.md` 或对应审阅记录；不要创建独立派发账本。

阶段 7 已批准实施编排存在安全并行包时，默认一个实施包对应一个运行时任务。Sub Agent 不得自行扩大写入范围、拆分目标或提前执行未满足依赖的任务。发现需要补充目标时，先返回路径、必要性与影响，由主 Agent 按核心 Skill 的变更分级裁决：必要实现补充由主 Agent 接管，或在确认无重叠后明确更新运行时任务范围；实质变化只暂停受影响任务及下游，返回相应阶段。工具不可用或收益下降时，主 Agent 可以按原顺序接管。

## 阶段 6 独立审阅

阶段 6 任务输入为三份正式文档、原始 PRD、当前技术依据和判断结论所需的最小仓库证据。不要向审阅者提供主 Agent 的预期结论、猜测或拟议修复。

返回先列有证据的阻塞发现，没有发现时明确审阅边界和无发现结论。审阅者不得编辑文件、定义新产品语义或批准确认节点。

主 Agent 只读核实发现。需要修改正式文档时，先按核心 Skill 获得返修决定；最终内容确定后，原 reviewer 仍可调用时只做一次聚焦复审。不可调用时用新的干净 reviewer 对当前完整输入重新审阅，不续写旧结论。

跨对话状态只更新 `consistency_review`：当前规划指纹、reviewer 引用、`attempt`、结果和精简结论。完整结论且指纹未变时复用；任务不可继续、失败或无完整结论时覆盖 reviewer 并将 `attempt` 从 1 增至 2。第二次仍不能形成完整结论时记为 `blocked`。规划指纹变化时清除旧结论，并从新输入的第一次审阅开始。

## 阶段 7 终结代码审阅

只有完整变更清单、输出指纹和全部批准验证项的实际结果均已记录，且 `implementation_result.status` 为 `implemented` 或 `verified` 时才能派发；结果允许包含 `failed` 和 `blocked`，无需等待其解决。任务包必须带上这些问题的原因、证据及未覆盖范围。派发后不得继续修改产品代码。

审阅者从完整变更清单进入，只扩展到判断正确性所需的最小调用方、owner、传播边界和项目规则；对照已批准契约、测试义务、实施边界和验证结果，优先检查错误行为、回归、状态或数据错误、生命周期/并发问题、安全风险和遗漏验证。对必要实现补充核对其依据、累计影响与验证，不得仅因路径未在原方案中命名就判定越界。纯风格偏好不作为发现。

返回先列按严重度排序的发现，每项包含文件或符号证据、影响和触发条件；没有发现时说明边界、无发现结论与验证盲区。审阅者不得编辑文件或实施修复。

主 Agent 只检查结果是否完整并绑定当前终结输入指纹。`findings` 与 `no_findings` 都是有效终态，与验证失败和条件不足项一并向用户汇报，不自动修复；验证未全通过也可完成模块流程，保留真实验证状态。跨对话状态只更新 `post_implementation_review`，恢复规则与阶段 6 相同：丢失或失败的第一次 reviewer 可由第二个全新 reviewer 对相同输入执行一次完整审阅，不保存替代关系；第二次仍失败则 `blocked`。代码、规划或验证变化时清除旧结论，并对新的终结输入重新开始审阅。

## 执行边界与停止条件

- Sub Agent 不得新增产品语义、自行扩大运行时授权范围、改变已批准规则或跨越确认节点。
- 只读任务不得编辑文件；写入任务只能修改明确授权目标。
- 新发现会改变上游规则、外部契约、依赖、实质风险或目标归属时，停止相关写入并返回主 Agent，不自行回退整个需求。
- 发现写入范围重叠时停止后启动或越界的任务，由主 Agent 检查已产生改动。
- 两个调查结论冲突时由主 Agent 根据权威来源裁决，不增加第三个 Agent 投票。
- 首次调查或实施结果可向原 Agent 发送一次聚焦补全；仍错误、缺证据或越界时由主 Agent 接管。强制审阅按各自两次尝试上限处理，不能由主 Agent 自审通过。
- 协调和复核成本已经不低于预计节省时间时，停止继续派发并串行完成。

## 结果回收

主 Agent 只吸收精简结论，不复制原始跟踪信息、长日志或完整工具输出。对关键事实、写入范围和验证结果做必要复核；解决冲突后再处理共享接缝与整合。实施偏差按核心 Skill 分级处理；改变上游规则或批准边界的实质变化返回对应确认节点，不静默合并。
