# 测试文档写作指南

本参考文件扩展父级 `SKILL.md` 的核心文档规则，不替代或覆盖这些规则。仅在编写或实质修订 `test.md` 前读取。

## 核心审阅问题

围绕已批准 Spec 的每项关键契约，结合项目实际需要展开哪些业务前置、真实触发和外部结果，才能让后续实施完整理解需求而不扩展产品契约或预设内部方案？

## 成文依据

测试文档紧随 Spec，在选择实施方案之前形成；其用途是以 GWT 场景补充需求、供实施方案参考，不指导真实测试执行。写入前确认：

- 已批准且仍有效的 Spec 是产品行为的唯一权威，每条关键 `R-*` 都已识别；
- 已按 [技术依据核对](technical-grounding.md#阶段-4-测试依据门槛) 定位相关 owner、真实业务入口、状态差异和受影响的既有行为；
- 需求事实、当前代码事实和预期行为已区分；现有代码与 Spec 冲突时，测试以 Spec 为期望，并把冲突标为受影响回归或待改行为；
- 不依赖 `implementation.md`、`I-*` 或尚未批准的未来文件、符号和内部调用顺序。

## 场景准入

本节是行为测试准入的具体定义。每个行为场景只能来自以下三类之一，并在工作笔记中保留来源分类与最小依据：

- 已批准 `R-*` 的直接外部结果；
- 有证据且本次变更必须保留的既有外部回归；
- 已知会产生不同已批准结果的真实业务入口。

失败、恢复、重复、乱序、生命周期或账户边界只有满足上述条件时才形成行为场景，否则保留为实施约束。场景只定义业务前置、真实触发和外部可观察结果，不选择测试层级、内部断言或生产实现机制。

请求次数、防御性拷贝、token/generation、同步、缓存内部状态、线程与架构结构等内部性质，除非本身对应已批准的外部契约，否则不生成 `T-*`。它们可以作为 Implementation 约束，并在代码实施阶段选择必要的实现级测试，但不能反向要求 Spec 定义新行为。

发现某个必要的外部可观察结果尚未由 Spec 定义时，返回阶段 3 明确契约，不在测试场景中替用户作产品决策。

## 覆盖边界

正文只保留从契约和项目实际展开的行为测试用例、受影响回归及必要的规则引用，不重复 Spec。返修时另按主 Skill 的[文档修订记录](../SKILL.md#文档修订记录)保留本轮改动。

- UI 变化属于 Spec 契约时，只把可观察结果写入对应行为场景，不建立独立 UI 或手工检查清单。
- 必要的业务状态写入 Given，例如已选照片、近期成功记录；失败及恢复写成业务可识别的触发和结果，不说明如何准备设备、构造数据或注入故障。
- 不写测试准备、现有验证入口、待实施验证目标、命令、测试基础设施或执行结果，也不因缺少自动化而派生新增测试任务。

## 从契约展开情况

先把每条关键 `R-*` 映射到至少一个可观察场景，再依据已确认的业务差异、真实入口或受影响回归拆分必要分支。只保留通过场景准入且会改变外部结果的组合；合并结果等价的排列，避免无差别枚举通用异步、生命周期或账户组合。

## 行为测试用例

使用 Markdown 标题和 Given-When-Then 分组列表描述外部可观察行为。场景标题使用比所属覆盖章节低一级的标题；位于“行为测试用例”下时默认使用三级标题。只有场景会被其他位置引用时才添加 `T-*` ID，否则标题只保留场景名称：

```markdown
### T-01 · <场景>

**Given**

- <业务状态或前置条件>

**When**

- <操作或触发条件>

**Then**

- <外部可观察结果>
```

每个条件、动作或结果单独使用一个列表项。从主路径开始，只添加有意义的分支、负向行为、恢复过程、可见状态变化和受影响回归。`When` 必须写可观察或业务可识别的真实触发，例如完成某项操作、返回页面或刷新失败，不能只写“状态变化”或“收到通知”。场景标题或相邻说明应能追溯到相关 `R-*`，但不要复制规则正文。合并等价变体。行为场景中不要出现符号、文件路径、Fake、挂载细节或内部调用顺序。

## 覆盖审阅

- 每条关键 `R-*` 都有可追溯的行为场景；仅在映射不明显时增加汇总表。会被下游引用或约束实施职责的场景使用稳定的 `T-*`，由实施文档承接。
- 全部场景通过上述准入；没有用笼统刷新场景掩盖已知业务差异，也没有保留结果等价的排列。
- 场景只补充需求理解，没有混入测试执行方法或验证能力建设要求。
- 按主 Skill 的文档写作基线删减后再提交审阅。
