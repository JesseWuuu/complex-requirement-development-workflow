# Figma 依据核对

仅当需求提供 Figma 或明确依赖 Figma 行为时读取本参考文件。只检查受影响流程所需的最小目标。

## 阶段 1：范围

验证访问权限，并确定范围内的准确文件、页面、Frame、Component 或 Node。深入检查前，先将宽泛链接收窄到具体目标。本阶段只使用设计确认目标和方案边界。

## 阶段 2：证据

只检查会影响产品契约、实施归属或验证的事实：

- 受影响的布局、Component、Variant、Token、资源和宿主约束；
- 可见状态、内容规则、输入、触控目标和无障碍；
- 设计呈现的导航、Overlay、手势或动效；
- 需求或既有行为要求、但设计未覆盖的运行时状态及其依据。

将这些事实与需求、仓库 UI 和项目规范对照。保留准确的目标链接或 Node ID，但不要倾倒 Figma 树、原始属性或未受影响的 Frame。

## 权威与下游使用

权威顺序遵循主 Skill。本参考文件只补充以下 Figma 使用边界：

- 仓库代码与规范决定当前行为、可复用 Component 和实施约束；Figma 不覆盖这些技术事实。
- 在阶段 2 提出实质矛盾。缺少某个 Frame 不代表禁止实现必需的运行时状态。
- Spec 中只关联受其约束的 UI 状态或交互；测试文档仅把契约要求的 UI 变化写成普通 Given-When-Then 行为场景中的外部可观察结果，不增加独立 UI 或手工覆盖；实施计划只记录满足这些场景所需的受影响技术目标和复用决策，不重复设计事实。

无法访问会改变产品语义、实施归属或验证结论的重要设计证据时，明确记录缺口并继续可独立完成的分析或草稿；草稿在相关内容处标明未核实边界。依赖缺失证据的结论不得标为已核实，存在阻塞项的文档不得通过确认节点；非阻塞假设按主 Skill 处理。
