# 实施文档写作指南

本参考文件扩展父级 `SKILL.md` 的核心文档规则，不替代或覆盖这些规则。仅在编写或实质修订 `implementation.md` 前读取。


## 核心审阅问题

满足全部已批准契约和测试义务的最小真实 Diff 是什么，需要在哪些既有技术目标上做哪些变更？只有会消除歧义、控制风险或建立门槛时，才补充职责、依赖、结果、失败行为、安全/隐私或完成证据。

## 成文门槛

实施文档必须建立在已批准且仍有效的 Spec、测试文档与仓库依据上。写入前确认：

- 每个技术结论都能追溯到 `R-*`、相关 `T-*`、项目规则、设计事实或当前代码，不用猜测补全文件、符号、API 或系统。
- 已按 [技术依据核对](technical-grounding.md) 确认适用规则、真实 owner、完整读写/清理影响面、触发与失败语义，并通过阶段 5 退出门槛。
- `test.md` 已基于当前项目逻辑定义关键行为场景、准备条件和真实可执行的命令；实施方案能够让这些场景对应的产品行为落地并可验证。
- 每个关键 `T-*` 已完成“真实入口或状态生产者 → owner → 传播或失效边界 → 可观察消费方”的职责走查；需要变化的环节已有已核实的技术目标与职责并将在成文时落到具体 `I-*`，声称由现有行为满足的环节有当前代码依据。
- 方案从阶段 2 的最小修改假设出发；每个偏离项都有新证据，并已更新技术依据结论。
- 会改变产品行为、外部契约、范围、安全、隐私或合规义务的问题已经回到上游确认。
- 若测试场景暴露 Spec 未定义的可观察行为，先返回阶段 3；若只需修正覆盖、准备或测试义务，先返回阶段 4。不得在实施文档中替测试做产品决策或静默删减覆盖。
- 仍未解决且会改变技术方案、文件范围、依赖顺序、失败行为或验证方式的问题属于阻塞项；先解决问题，不生成看似可执行的方案。
- 只允许保留主 Skill 定义的非阻塞假设，并写明其适用范围和判断错误时的局部影响。

成文过程中可以在工作笔记中维护精简的 `T-* → 真实入口 → owner → 既有保证或 I-* → 验证目标` 责任映射。它用于证明没有测试义务落空，不直接复制进交付文档；只有多对多关系或既有/新增职责边界不明显时，才把必要映射写入正文。

## 最小 Diff 与新增目标负担证明

优先扩展现有职责边界。任何新增生产目标都必须通过 [技术依据核对](technical-grounding.md) 中的负担证明；正文只保留审阅新增目标所必需的结论，未通过则删除该目标。

方便测试、概念整洁、结构对称和未来复用不能单独证明新增目标的必要性。现有代码无需先被整理成理想结构；只要局部修改能满足契约和回归约束，就不为方案观感扩大变更。

共享 key、缓存或时间戳被用于并发屏障、已读标记或生命周期判断时，实施结论必须建立在全部相关读写和清理方已经核对的事实之上。不同来源或不同服务端结果的动作不能只因调用了相同 API 或使用相似名称就合并为统一副作用。

## 内容要求

### 1. 必要时定义整体结果

只有多个步骤的共同目标或总体完成边界无法从变更本身快速看出时，才在开头用一个短段落说明技术落地结果。只在边界容易误解时补充技术非目标。不要重复 Spec 的背景、产品规则或验收条件。

### 2. 建立契约、测试到变更的追溯

每个主要步骤使用 `I-*`。每个关键 `T-*` 必须能定位到至少一个负责变化的 `I-*`，或定位到经当前代码核实且无需修改的既有保证；后者只在容易误判时于技术边界中说明一次。步骤与产品规则或测试义务的关系不明显时，在步骤内标明相关 `R-*` 与 `T-*`；能从步骤名称、变更描述或相邻引用直接看出的，不增加“覆盖规则/测试”字段。一个步骤可以覆盖多条规则和测试，一条规则或测试也可以由多个步骤共同完成；只有多对多关系确实难以快速审阅时才增加精简映射表。

没有对应 `R-*` 或 `T-*` 的步骤必须能说明它是项目约束、集成需要、迁移需要或验证接缝；否则删除。不要为路径、辅助动作或单独验证动作创建无意义的 `I-*`。

实施文档不重写 Given-When-Then 场景，但必须让审阅者能确认：关键行为测试的真实触发会经过正确 owner 到达可观察消费方，测试准备和已核实命令不被方案破坏。只负责页面初始化的步骤不能承接动态更新、恢复、重复或乱序场景。若某个已批准测试只能通过改变范围或契约才能实现，返回上游重新审阅，不能将它改写为内部断言或模糊检查。

### 3. 命名真实的技术目标

在目标首次出现时给出足以定位职责的具体模块、文件、符号、API、数据存储或外部系统，并区分现有目标与建议新增目标。只列会修改、创建、删除或作为关键接缝使用的目标；不要输出仓库导览或重复文件清单。

如果精确文件或符号尚不能从仓库确认，写职责边界和候选落点并将不确定性按“成文门槛”处理，不要把推测写成事实。

对建议新增的目标明确标注“新增”，并提供负担证明结论，让审阅者可以判断它为何不能由既有目标内的局部修改替代。若建立新 owner，还必须说明不会复制已有权威数据、扩大无关行为或增加未交代的账户/进程清理义务。

只有代码漂移、工作区脏改动或可复现性会改变执行或验证结论时，才记录分支、commit 或工作区基线；否则省略。

### 4. 描述变更导向的实施步骤

按真实依赖顺序组织 `I-*`。每个步骤只需让执行者明确：

- **落点：** 哪个已核实的模块、文件、符号、API、数据存储或外部系统发生变化，以及它承担的必要职责；
- **变更：** 需要新增、修改、移除或迁移什么行为；
- **依赖：** 只写必须先存在且不能从顺序直接看出的接口、状态、数据或前序 `I-*`。

默认把落点、职责和变更合并成一个短段落或一个“变更”要点，不强制拆字段。以下内容均为按需补充：

- **覆盖规则/测试：** 只有 `R-*`、`T-*` 到变更的映射不明显或需要跨文档追溯时保留；
- **触发与传播：** 状态型或动态 `T-*` 涉及的业务生产者、生命周期入口、owner 与消费方不能从变更描述看出时保留；
- **结果：** 只有变更描述不足以说明完成后的稳定边界时保留；
- **失败行为：** 只有存在需要实施层明确的错误、取消、重试、恢复、兼容或安全停止机制时保留；
- **安全/隐私：** 只有存在实质影响、保护边界或易被误判的风险时保留；
- **完成证据：** 只有该步骤存在进入后续依赖项前必须满足的检查或产物时保留；完整验证仍归 `test.md`。

只在正确性依赖精确顺序时写操作级步骤。让执行者可以根据目标、约束和代码现状选择局部实现细节，不要把实施文档写成逐行编码教程。

### 5. 交代状态、数据与失败行为

只有本次变更改变状态、事件、生命周期、存储、网络、缓存、迁移或跨系统交互路径，或者这些路径对正确性构成非显然约束时，才说明输入如何经过关键边界形成输出，并只列受影响的成功、空值、错误、取消、重试、重复触发、恢复或兼容行为。优先用一个短流程或状态转换说明，再让 `I-*` 引用；未变化的既有路径不枚举，简单局部变更直接写在步骤内。

产品失败语义必须由 Spec 明确，实施文档不再重复。只有实现需要新增或改变技术保护时，才说明触发条件和处理方式；可观察证据仅在它构成必要实施门槛时补充。涉及迁移、持久化或不可逆操作时，仍需补充回滚、前向修复或安全停止条件。

### 6. 评估安全、隐私与外部影响

必须检查权限、凭据、敏感数据、日志、外部服务、数据保留、破坏性操作和兼容性影响。存在实质影响时，写明保护边界、失败策略和验证责任；不存在影响且审阅者不太可能误判时省略。不要添加只有“无”或“不适用”的形式化章节。

### 7. 只保留必要的实施门槛

不要求每个 `I-*` 都写“完成证据”。只有某项检查或产物决定能否进入后续步骤，或者属于该变更不可分割的生成、迁移或配置动作时，才在对应步骤记录验证责任和预期信号。

完整行为场景、测试数据/环境准备、受影响回归和当前已存在的测试命令目录归已批准的 `test.md`。由于测试文档先形成，它不引用 `I-*`；实施文档按需引用关键 `T-*`，说明由哪些变更满足测试义务，但不复制既有命令、场景或证据。若 `test.md` 声明了待实施验证目标，对应 `I-*` 必须命名要新增或扩展的真实技术目标、计划执行入口、集成边界和通过信号；这是实施变更本身，不属于重复测试命令。

## 推荐模板

以下是默认骨架，不是必填章节清单。删除不适用的占位项；如果一个短段落已经能清楚表达，不要拆成更多标题。

```markdown
# <功能名称>实施文档

> 产品规则：[spec.md](./spec.md) · 测试方案：[test.md](./test.md)

## 技术边界

<只在多个步骤共享职责边界、集成接缝、数据流或状态转换时保留。简单变更省略本节。>

## 实施步骤

### I-01 · <变更导向的步骤名称>

- **变更：** `<path-or-resource>` / `<symbol-or-api>` — <需要新增、修改、移除或迁移的行为，以及理解该变更所必需的职责>
- **依赖：** <前序 I-*、接口、状态或数据；无非显然依赖则删除>

<只有确有审阅或执行价值时，才补充覆盖规则/测试、结果、状态/数据流、失败行为、安全/隐私或完成证据；不建立空字段。>

### I-02 · <下一步骤名称>

<继续聚焦变更，只保留必要依赖和真正有价值的可选信息。>

## 风险与共享边界

<只记录跨多个 I-* 的风险、共享写入点、外部契约、迁移/回滚或兼容边界。局部风险留在所属步骤；没有则删除本节。>

## 实施编排

<仅在满足下述“实施编排”条件时添加。>

## 开放问题与非阻塞假设

- **<问题或假设>：** <适用范围、当前处理、责任方，以及判断错误时的局部影响。>

<没有可保留项则删除本节；阻塞问题不得留在可批准的实施文档中。>
```

## 实施编排

当派发检查识别出安全并行的实施包，或者依赖、共享接缝与集成风险要求分批实施时，在 `implementation.md` 中增加“实施编排”。简单且强串行的任务省略本节；没有安全并行边界但确需分段控制风险时，只规划串行批次，不分配 Sub Agent。

实施编排是供用户审阅的执行设计，不是实时派发记录，也不代表已经获得产品代码写入授权。使用完成任务所需的最少批次，通常按“共享基线 → 独立实施包 → 集成与验证”组织，但不要为了凑齐固定结构增加空批次。每个批次或实施包只记录：

1. 目标结果及包含的 `I-*`；
2. 进入条件、前置依赖和完成条件；
3. 负责角色，即主 Agent 或 Sub Agent 任务包；
4. 唯一写入范围、禁止触碰的共享目标和主 Agent 负责的集成点；
5. 验证责任、预期证据和向下一批次移交的最小产物。

并行编排必须遵守主 Skill 的阶段配额。超出配额的 `I-*` 保留依赖顺序并由主 Agent 串行处理，不要拆成候补 Sub Agent。依赖未满足的包不得进入同一并行批次；同一文件不得分给多个写入负责人。

实际 Agent ID、运行状态、等待或重试过程、修订次数和工具日志属于运行时派发清单，不写入 `implementation.md`。父级 Skill 规定的阶段 7 终结只读代码审阅也是固定的运行时收尾动作，不属于实施步骤、实施编排或验证要求，不在本文档中登记。

阶段 7 符合核心 Skill 判据的必要实现补充只登记实施结果及运行时写入范围，不为追认新增配套文件而改写已批准的实施文档或编排；实质方案变化仍需修订和复审。此规则不降低规划时核实具体目标与证明新增目标必要性的要求。

## 实施上下文包

仅在工作交接或全新上下文恢复任务时，且正文与实施编排仍不足以定位工作时添加“实施上下文包”。只保留尚不明显的最小入口文件、核心符号、允许范围、修订边界和验收检查链接；不要仅因存在并行包就添加，也不要重复实施编排字段。

## 交付前删减与完整性检查

交付前逐项确认：

- 每条 `I-*` 都聚焦命名技术目标上的具体变更；需要追溯的 `R-*` 与 `T-*` 能定位到相应变更，且没有无依据的步骤；
- 所有命名路径、符号、API 和系统均已由当前仓库或明确设计依据核实；
- 每个新增生产目标都完成负担证明；若删除后仍能满足全部已批准需求与回归约束，已经删除；共享状态已经核对完整读写/清理影响面；
- 顺序与依赖可执行，共享接缝只有一个明确负责人；
- 状态/数据流、失败行为、回滚或安全停止条件只在影响实施正确性时保留，并且已明确；
- 安全、隐私和外部影响已经评估，只有实质风险或易误判边界写入文档；
- 已批准的行为场景、准备条件与执行目标可以由方案满足，没有被静默删除、弱化或改写；
- 每个关键 `T-*` 都能沿真实入口、状态生产或失效方、owner、传播边界到达可观察消费方；动态场景没有被只处理初始化的步骤冒领，既有保证均有当前代码依据；
- 必要的实施门槛有完成证据，其他验证由 `test.md` 负责且没有重复；
- 没有阻塞问题、过程历史、废弃方案、实时状态、通用建议或空章节。
