# 实施文档写作指南

本参考文件扩展父级 `SKILL.md` 的核心文档规则，不替代或覆盖这些规则。仅在编写或实质修订 `implementation.md` 前读取。


## 核心审阅问题

满足全部已批准契约及其场景化行为要求的最小真实 Diff 是什么，需要在哪些既有技术目标上做哪些变更？只有会消除歧义、控制风险或建立门槛时，才补充职责、依赖、结果、失败行为、安全/隐私或完成证据。

## 成文门槛

实施文档以已批准且仍有效的 Spec、测试文档为输入，写入前通过 [技术依据核对的阶段 5 退出门槛](technical-grounding.md#阶段-5-写入退出门槛)。技术走查、最小修改假设和新增目标评估均由该参考定义，本指南只规定如何把已收口结论写成可执行变更。

发现产品契约缺口时返回阶段 3；真实业务情况遗漏或场景准入错误返回阶段 4；技术依据不足时继续定向核对，不用推测补成看似可执行的方案。验证方式由本阶段按需判断，不作为 Test 缺口回退。只保留主 Skill 允许的非阻塞假设，并说明范围及判断错误时的局部影响。

## 内容要求

### 1. 必要时定义整体结果

只有多个步骤的共同目标或总体完成边界无法从变更本身快速看出时，才在开头用一个短段落说明技术落地结果。只在边界容易误解时补充技术非目标。不要重复 Spec 的背景、产品规则或验收条件。

### 2. 建立契约、场景到变更的追溯

每个主要步骤使用 `I-*`。每个关键 `T-*` 必须能定位到负责满足其行为的 `I-*`，或经当前代码核实且无需修改的既有保证；后者只在容易误判时说明一次。步骤与产品规则或场景的关系不明显时，标明相关 `R-*`、`T-*`；仅在多对多关系难以审阅时增加精简映射表，不复制完整工作笔记。

没有对应 `R-*` 或 `T-*` 的步骤必须能说明它是项目约束、集成需要、迁移需要或经必要性判断的验证接缝；否则删除。不要为路径、辅助动作或单独验证动作创建无意义的 `I-*`。

正文表达技术职责如何满足关键 `T-*`，不重写 Given-When-Then 场景。若满足场景中的行为必须改变范围或契约，返回上游重新审阅，不能静默删减场景或将其外部结果改写为内部断言。

### 3. 命名真实的技术目标

在目标首次出现时给出足以定位职责的具体模块、文件、符号、API、数据存储或外部系统，并区分现有目标与建议新增目标。只列会修改、创建、删除或作为关键接缝使用的目标；不要输出仓库导览或重复文件清单。

如果精确文件或符号尚不能从仓库确认，写职责边界和候选落点并将不确定性按“成文门槛”处理，不要把推测写成事实。

建议新增的目标明确标注“新增”，并保留 [与其实际影响相称的必要性评估](technical-grounding.md#最小修改与复用优先) 结论。局部辅助目标简要交代必要性、复用与影响；新增 owner、共享状态、依赖或跨生命周期机制保留完整评估中决定方案取舍和边界的结论，不复制逐项核对过程。

只有代码漂移、工作区脏改动或可复现性会改变执行或验证结论时，才记录分支、commit 或工作区基线；否则省略。

### 4. 描述变更导向的实施步骤

按真实依赖顺序组织 `I-*`。每个步骤只需让执行者明确：

- **落点：** 哪个已核实的模块、文件、符号、API、数据存储或外部系统发生变化，以及它承担的必要职责；
- **变更：** 需要新增、修改、移除或迁移什么行为；
- **依赖：** 只写必须先存在且不能从顺序直接看出的接口、状态、数据或前序 `I-*`。

默认采用“`I-*` 标题 → 编号事项 → 下级条目”的结构，让审阅者先看到要做什么，再按需展开细节：

- 每个 `I-*` 内按事项列出编号清单，一条聚焦一个可辨认的变更，以简短、加粗的动作标题开头；单一且简单的事项可以直接用一个条目写清，不强行编号或嵌套。
- 将该事项的技术落点、具体变更、触发条件、例外和保护约束放在所属事项下，用无序条目分别表达；不把多个动作或条件挤进同一长段落、同一“变更”要点或表格单元格。
- 同级条目表达并列事项，下级条目只解释其父项。仅在存在真实从属关系时继续缩进，不把并列事项伪装成子项，也不为每句话新增标题或固定字段。
- 编号用于组织事项；只有真实依赖要求时才规定严格执行顺序，不因排版引入新的依赖。新增目标必要性、共享职责等说明可保留为短段落或独立要点，与待办事项区分。
- 按必要实施门槛保留的检查放在对应事项下，写清必要条件与通过信号，不为套用格式新增验证章节。

以下内容均为按需补充，放在所属事项下；适用于整个 `I-*` 时在该步骤内集中说明一次：

- **关联规则/场景：** 只有 `R-*`、`T-*` 到变更的映射不明显或需要跨文档追溯时保留；
- **触发与传播：** 状态型或动态 `T-*` 涉及的业务生产者、生命周期入口、owner 与消费方不能从变更描述看出时保留；
- **结果：** 只有变更描述不足以说明完成后的稳定边界时保留；
- **失败行为：** 只有存在需要实施层明确的错误、取消、重试、恢复、兼容或安全停止机制时保留；
- **安全/隐私：** 只有存在实质影响、保护边界或易被误判的风险时保留；
- **完成证据：** 只有该步骤存在进入后续依赖项前必须满足的检查或产物时保留。

只在正确性依赖精确顺序时写操作级步骤。让执行者可以根据目标、约束和代码现状选择局部实现细节，不要把实施文档写成逐行编码教程。

### 5. 交代状态、数据与失败行为

只有本次变更改变状态、事件、生命周期、存储、网络、缓存、迁移或跨系统交互路径，或者这些路径对正确性构成非显然约束时，才说明输入如何经过关键边界形成输出，并只列受影响的成功、空值、错误、取消、重试、重复触发、恢复或兼容行为。优先用一个短流程或状态转换说明，再让 `I-*` 引用；未变化的既有路径不枚举，简单局部变更直接写在步骤内。

产品失败语义必须由 Spec 明确，实施文档不再重复。只有实现需要新增或改变技术保护时，才说明触发条件和处理方式；可观察证据仅在它构成必要实施门槛时补充。涉及迁移、持久化或不可逆操作时，仍需补充回滚、前向修复或安全停止条件。

### 6. 评估安全、隐私与外部影响

必须检查权限、凭据、敏感数据、日志、外部服务、数据保留、破坏性操作和兼容性影响。存在实质影响时，写明保护边界、失败策略和验证责任；不存在影响且审阅者不太可能误判时省略。不要添加只有“无”或“不适用”的形式化章节。

### 7. 只保留必要的实施门槛

不要求每个 `I-*` 都写“完成证据”。只有某项检查或产物决定能否进入后续步骤，或者属于该变更不可分割的生成、迁移或配置动作时，才在对应步骤记录验证责任和预期信号。

`test.md` 提供行为场景，`T-*` 到 `I-*` 的追溯用于说明如何满足需求，不代表每个场景都要新增自动化或手工执行任务。不要把测试准备、命令清单或验证能力盘点整体搬入本文。

必要验证按项目规则与实际改动风险选择。新增自动化测试、测试依赖或生产测试接缝时，说明要防止的具体错误、现有手段的不足与最小新增范围；仅有 GWT 场景或缺少自动化不能证明新增的必要性。常规验证在阶段 7 按实际改动执行并记录，本文只保留影响实施方案或步骤依赖的验证决策。

## 推荐模板

以下是默认骨架，不是必填章节清单。删除不适用的占位项；事项数量和层级由实际变更决定，简单事项保持单条，说明性文字可以使用短段落。

```markdown
# <功能名称>实施文档

> 产品规则：[spec.md](./spec.md) · 行为场景：[test.md](./test.md)

## 技术边界

<只在多个步骤共享职责边界、集成接缝、数据流或状态转换时保留。简单变更省略本节。>

## 实施步骤

### I-01 · <变更导向的步骤名称>

1. **<具体动作名称>。**

   - 在 `<path-or-resource>` / `<symbol-or-api>` <新增、修改、移除或迁移的行为，以及必要职责>。
   - <该事项的触发条件、例外或保护约束；有多个并列要求时分别列出，无则删除。>

2. **<另一个具体动作名称>。**

   - <对应的真实技术目标与变更。>
   - <只有存在非显然依赖时，说明前序 I-*、接口、状态或数据。>

<新增目标必要性或整个步骤共享的边界在此简短说明；无需逐项重复。确有追溯价值时标明相关 R-*、T-*。>

### I-02 · <下一步骤名称>

- **<单一且简单的动作>：** 在 `<path-or-resource>` / `<symbol-or-api>` <具体变更；无需额外层级即可写清时使用单条>。

## 风险与共享边界

<只记录跨多个 I-* 的风险、共享写入点、外部契约、迁移/回滚或兼容边界。局部风险留在所属步骤；没有则删除本节。>

## 实施编排

<仅在满足下述“实施编排”条件时添加。>

## 开放问题与非阻塞假设

- **<问题或假设>：** <适用范围、当前处理、责任方，以及判断错误时的局部影响。>

<没有可保留项则删除本节；阻塞问题不得留在可批准的实施文档中。>

## 修订记录

<发生返修时按主 Skill 的“文档修订记录”追加日期、原因、涉及章节或既有 ID 及具体改动摘要，保留既有记录；首次成文且尚未返修时删除本节。>
```

## 实施编排

当派发检查识别出安全并行的实施包，或者依赖、共享接缝、集成风险或用户审阅需要分批实施时，在 `implementation.md` 中增加“实施编排”。每批应形成用户可检查的阶段结果，不机械地按文件、每个 `I-*` 或小改动拆批。简单且强串行的任务可省略本节，默认全部 `I-*` 作为一个批次，实施及必要验证记录完成后自动结束；没有安全并行边界但确需分段时，只规划串行批次，不分配 Sub Agent。

实施编排是供用户审阅的执行设计，不是实时派发记录，也不代表已经获得产品代码写入授权。使用完成任务所需的最少批次，通常按“共享基线 → 独立实施包 → 集成与验证”组织，但不要为了凑齐固定结构增加空批次。每批使用简短、稳定的业务或技术结果名称，并明确包含的实施包；实施包是批内执行单位，非最后批是用户审阅单位，最后一批是自动收尾单位。每个批次或实施包只记录：

1. 目标结果及包含的 `I-*`；
2. 进入条件、前置依赖和完成条件；后一批的进入条件包含前批用户通过；
3. 负责角色，即主 Agent 或 Sub Agent 任务包；
4. 唯一写入范围、禁止触碰的共享目标和主 Agent 负责的集成点；
5. 验证责任、预期证据和向下一批次移交的最小产物；非最后批明确供用户审阅的结果边界，最后一批明确完成边界。

同一批次中的任务全部回收、完成集成和必要验证后才视为整批完成；非最后批统一停下供用户审阅，最后一批自动收尾。最后一批须涵盖必要的整体集成验证与遗留问题汇总；能与已有批次合并时不另增空的收尾批次。非最后批用户通过后才可开始下一批，不把一次产品代码授权解释为允许连续执行全部批次。

并行编排遵循 [委派参考的收益门槛与数量](subagent-delegation.md#收益门槛与数量)。超出配额的 `I-*` 保留依赖顺序并由主 Agent 串行处理，不要拆成候补 Sub Agent。依赖未满足的包不得进入同一并行批次；同一批内同一文件不得分给多个写入负责人。后批可按已批准依赖继续修改前批文件，由该批的唯一负责人接手。

实际 Agent ID、运行状态、等待或重试过程、Sub Agent 任务返工次数和工具日志不写入 `implementation.md`。用户审阅的批次状态、输出版本与批准记录保存在[检查点](cross-conversation-resumption.md)，不另建派发账本；文档本身的返修仍须按主 Skill 的[文档修订记录](../SKILL.md#文档修订记录)保留。阶段 7 在最后一批实施及必要验证记录完成后自动收尾，不规划独立代码审阅。

阶段 7 符合[实施变更分级](code-execution.md#实施中的变更分级)的必要实现补充只登记实施结果及运行时写入范围，不为追认新增配套文件而改写已批准的实施文档或编排；实质方案变化仍需修订和复审。此规则不降低规划时核实具体目标与证明新增目标必要性的要求。

## 实施上下文包

仅在工作交接或全新上下文恢复任务时，且正文与实施编排仍不足以定位工作时添加“实施上下文包”。只保留尚不明显的最小入口文件、核心符号、允许范围、修订边界和验收检查链接；不要仅因存在并行包就添加，也不要重复实施编排字段。

## 交付前删减与完整性检查

交付前逐项确认：

- 每条 `I-*` 都聚焦已核实技术目标上的具体变更，关键规则与场景能定位到相应变更或既有保证；
- 实施事项、条件和约束按上述版式组织，没有为排版增加步骤、层级或依赖；
- 技术依据的阶段 5 退出门槛仍成立；必要的职责、依赖、风险和新增目标评估结论已落入正文；
- 已批准场景的行为要求均由方案承接；验证决策有项目规则或具体风险依据，没有从场景数量派生测试工作；
- 按主 Skill 的文档写作基线删除重复内容和非交付信息，没有遗留阻塞问题。
