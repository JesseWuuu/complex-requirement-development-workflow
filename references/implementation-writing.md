# 实施计划写作指南

编写或修订 `implementation.md` 时读取，包括表达与版式调整；成文门槛与返修处理遵循主 Skill。

## 核心审阅问题

满足全部已批准契约及其场景化行为要求的最小真实 Diff 是什么，需要在哪些既有技术目标上做哪些变更？只有会消除歧义、控制风险或建立门槛时，才补充职责、依赖、结果、失败行为、安全/隐私或完成证据。

## 成文门槛

实施计划以已批准且仍有效的 Spec、测试文档和实现思路为输入，通过 [技术依据核对的阶段 6 退出门槛](technical-grounding.md#阶段-6-写入退出门槛) 后成文。技术走查、最小修改假设和新增目标评估均由该参考定义，本指南只规定如何把已收口结论写成可执行变更。

发现核心职责、路径或重要取舍需要改变时返回阶段 5；局部文件、方法和执行约束在本阶段细化，不为普通细化重开实现思路。发现产品契约缺口时返回阶段 3；真实业务情况遗漏或场景准入错误返回阶段 4；技术依据不足时继续定向核对，不用推测补成看似可执行的方案。验证方式由本阶段按需判断，不作为 Test 缺口回退。只保留主 Skill 允许的非阻塞假设，并说明范围及判断错误时的局部影响。

## 内容要求

### 1. 承接已批准的实现思路

开头链接 `technical-design.md`，不重写整体链路和方案取舍。本文负责把思路落实到具体目标、变更、依赖和批次，并完整保留执行所需的请求控制、恢复顺序、失败处理等约束；不能以“思路已解释”为由只留模糊引用。新增局部目标的必要性说明仍放在所属步骤。

### 2. 建立契约、场景到变更的追溯

每个主要步骤使用 `I-*`。每个关键 `T-*` 必须能定位到负责满足其行为的 `I-*`，或经当前代码核实且无需修改的既有保证；后者只在容易误判时说明一次。步骤与产品规则或场景的关系不明显时，标明相关 `R-*`、`T-*`；仅在多对多关系难以审阅时增加精简映射表，不复制完整工作笔记。

没有对应 `R-*` 或 `T-*` 的步骤必须能说明它是项目约束、集成需要、迁移需要或经必要性判断的验证接缝；否则删除。不要为路径、辅助动作或单独验证动作创建无意义的 `I-*`。

正文表达技术职责如何满足关键 `T-*`，不重写 Given-When-Then 场景。若满足场景中的行为必须改变范围或契约，返回上游重新审阅，不能静默删减场景或将其外部结果改写为内部断言。

### 3. 命名真实的技术目标

在目标首次出现时给出足以定位职责的具体模块、文件、符号、API、数据存储或外部系统，并区分现有目标与建议新增目标。只列会修改、创建、删除或作为关键接缝使用的目标；不要输出仓库导览或重复文件清单。

如果精确文件或符号尚不能从仓库确认，写职责边界和候选落点并将不确定性按“成文门槛”处理，不要把推测写成事实。

建议新增的目标明确标注“新增”，并保留 [与其实际影响相称的必要性评估](technical-grounding.md#最小修改与复用优先) 结论。局部辅助目标简要交代必要性、复用与影响；新增 owner、共享状态、依赖或跨生命周期机制保留完整评估中决定方案取舍和边界的结论，不复制逐项核对过程。

只有代码漂移、工作区脏改动或可复现性会改变执行或验证结论时，才记录分支、commit 或工作区基线；否则省略。

### 4. 描述变更导向的实施步骤

按真实依赖顺序组织 `I-*`。每个步骤只需让执行者明确：

- **落点：** 哪个已核实的模块、文件、符号、API、数据存储或外部系统发生变化，以及它承担的必要职责；
- **变更：** 由谁在什么条件下，对哪个对象新增、修改、移除或迁移什么行为；上下文已明确的主语和条件无需逐条重复；
- **依赖：** 只写必须先存在且不能从顺序直接看出的接口、状态、数据或前序 `I-*`。

标题和正文用具体动作表达变更；“状态归并”“接缝”“消费”等术语不能代替行为说明，含义无法从上下文判断时就地解释。默认采用“`I-*` 标题 → 编号事项 → 下级条目”的结构，让审阅者先看到要做什么，再按需展开细节：

- 每个 `I-*` 内按事项列出编号清单，一条聚焦一个可辨认的变更，以简短、加粗的动作标题开头；单一且简单的事项可以直接用一个条目写清，不强行编号或嵌套。
- 将该事项的技术落点、具体变更、触发条件、例外和保护约束放在所属事项下，用无序条目分别表达；不把多个动作或条件挤进同一长段落、同一“变更”要点或表格单元格。
- 同级条目表达并列事项，下级条目只解释其父项。仅在存在真实从属关系时继续缩进，不把并列事项伪装成子项，也不为每句话新增标题或固定字段。
- 编号用于组织事项；只有真实依赖要求时才规定严格执行顺序，不因排版引入新的依赖。新增目标必要性、共享职责等说明可保留为短段落或独立要点，与待办事项区分。
- 按必要实施门槛保留的检查放在对应事项下，写清必要条件与通过信号，不为套用格式新增验证章节。

规则追溯、状态与失败处理、外部影响和实施门槛按各节要求放在所属事项下；整个 `I-*` 共用的约束集中说明一次。变更描述不足以说明生产者、触发入口、传播过程或完成后的稳定结果时，才补充这些信息。

只在正确性依赖精确顺序时写操作级步骤。让执行者可以根据目标、约束和代码现状选择局部实现细节，不要把实施计划写成逐行编码教程。

### 5. 交代状态、数据与失败行为

只有本次变更改变状态、事件、生命周期、存储、网络、缓存、迁移或跨系统交互路径，或者这些路径对正确性构成非显然约束时，才说明输入如何经过关键边界形成输出，并只列受影响的成功、空值、错误、取消、重试、重复触发、恢复或兼容行为。未变化的既有路径不枚举，简单局部变更直接写在步骤内。

正文中需要交代的状态或数据，应能看出所属对象、维护方和用途。同一流程涉及容易混淆的状态维度时，说明各自含义与关系，例如组件展示、单次请求进展与业务进度。影响操作或恢复的阶段，应能判断进入与退出条件、允许操作，以及失败后的停留位置和重试对象。按需用短流程或状态对照表集中说明，再让相关 `I-*` 引用；这不要求新增状态机或枚举无关状态。

产品失败语义由 Spec 定义，按需引用，不在实施计划重新定义或全文复述。只有实现需要新增或改变技术保护时，才展开触发条件和处理方式；可观察证据仅在它构成必要实施门槛时补充。涉及迁移、持久化或不可逆操作时，仍需补充回滚、前向修复或安全停止条件。

### 6. 评估安全、隐私与外部影响

根据本次变更判断是否涉及权限、凭据、敏感数据、日志、外部服务、数据保留、破坏性操作或兼容性。存在实质影响时，写明保护边界、失败策略和验证责任；无关项省略，不为此开展全量安全审计或添加只有“无”“不适用”的章节。

### 7. 只保留必要的实施门槛

不要求每个 `I-*` 都写“完成证据”。只有某项检查或产物决定能否进入后续步骤，或者属于该变更不可分割的生成、迁移或配置动作时，才在对应步骤记录验证责任和预期信号。

`test.md` 提供行为场景，`T-*` 到 `I-*` 的追溯用于说明如何满足需求，不代表每个场景都要新增自动化或手工执行任务。不要把测试准备、命令清单或验证能力盘点整体搬入本文。

必要验证按项目规则与实际改动风险选择。新增自动化测试、测试依赖或生产测试接缝时，说明要防止的具体错误、现有手段的不足与最小新增范围；仅有 GWT 场景或缺少自动化不能证明新增的必要性。常规验证在阶段 8 按实际改动执行并记录，本文只保留影响实施方案或步骤依赖的验证决策。

## 实施编排

存在安全并行的实施包，或依赖、共享边界、集成风险及用户审阅需要分批时，增加“实施编排”。每批应形成可检查的阶段结果，不机械地按文件、每个 `I-*` 或小改动拆批。简单且强串行的任务可省略本节，默认全部 `I-*` 为一个批次；确需分段但不能安全并行时，只规划串行批次。

实施编排是供用户审阅的执行设计，不是实时派发记录或产品代码授权。按真实依赖使用最少批次，不为“共享基线 → 独立实施包 → 集成与验证”等参考结构增加空批次。每批使用稳定的结果名称，实施包是批内执行单位；以下信息在适用的批次或包层级记录一次：

1. 目标结果及包含的 `I-*`；
2. 进入条件、前置依赖和完成条件；后一批的进入条件包含前批用户通过；
3. 负责角色，即主 Agent 或 Sub Agent 任务包；
4. 唯一写入范围、禁止触碰的共享目标和主 Agent 负责的集成点；
5. 验证责任、预期证据和必要移交产物。

每批明确可审阅结果或完成边界，全部任务回收、集成并完成必要验证后才能交付。非最后批由用户通过后进入下一批；最后一批涵盖必要的整体集成验证和遗留问题汇总，按[实施规则](code-execution.md#最后一批与完成)自动收尾，不另增空的收尾批次。

并行编排遵循 [委派参考的收益门槛与数量](subagent-delegation.md#收益门槛与数量)。超出配额的 `I-*` 保留依赖顺序并由主 Agent 串行处理，不要拆成候补 Sub Agent。依赖未满足的包不得进入同一并行批次；同一批内同一文件不得分给多个写入负责人。后批可按已批准依赖继续修改前批文件，由该批的唯一负责人接手。

实际 Agent ID、运行状态、等待重试和工具日志不写入 `implementation.md`。批次状态、输出版本与批准记录保存在[检查点](cross-conversation-resumption.md)，不另建派发账本；文档返修记录按主 Skill 执行。

阶段 8 符合[实施变更分级](code-execution.md#实施中的变更分级)的必要实现补充只登记实施结果及运行时写入范围，不为追认新增配套文件而改写已批准的实施计划或编排；实质方案变化仍需修订和复审。此规则不降低规划时核实具体目标与证明新增目标必要性的要求。

## 实施上下文包

仅在工作交接或全新上下文恢复任务时，且正文与实施编排仍不足以定位工作时添加“实施上下文包”。只保留尚不明显的最小入口文件、核心符号、允许范围、修订边界和验收检查链接；不要仅因存在并行包就添加，也不要重复实施编排字段。

## 交付前删减与完整性检查

交付前逐项确认：

- 每条 `I-*` 都聚焦已核实技术目标上的具体变更，关键规则与场景能定位到相应变更或既有保证；
- 实施事项、条件和约束按上述版式组织，能从正文判断谁在何时处理什么、相关状态表示什么及如何转换，没有为排版增加步骤、层级或依赖；
- 技术依据的阶段 6 退出门槛仍成立；必要的职责、依赖、风险和新增目标评估结论已落入正文；
- 已批准场景的行为要求均由方案承接；验证决策有项目规则或具体风险依据，没有从场景数量派生测试工作；
- 按主 Skill 的文档写作基线删除重复内容和非交付信息，没有遗留阻塞问题。
