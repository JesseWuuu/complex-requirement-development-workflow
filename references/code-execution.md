# 阶段 7：分批实施、验证与用户审阅

仅在准备进入或恢复阶段 7、或处理实施偏差时读取。本文定义批次执行、用户审阅、实施变更分级与完成边界；派发方式见[委派参考](subagent-delegation.md)，记录方式见[跨对话续接](cross-conversation-resumption.md)。

## 进入与恢复

获得明确的产品代码实施授权后，先校验三份文档和技术依据指纹仍与授权绑定输入一致。工作区模块还必须用自己的 owner 执行活动槽 `check`；已经失去活动槽或另一个模块正在实施时，不得开始代码写入。

从已批准 `implementation.md` 的实施编排建立有序批次，沿用文档中的批次名称和 `I-*`，不另造 ID。没有编排的简单任务作为一个批次，由主 Agent 按 `I-*` 串行完成。阶段 7 不自行合并、拆分或跳过已批准的用户审阅边界；需要调整时先明确影响并取得用户对新边界的确认，改变技术依赖或其他实质方案时按下文回退。

首次授权允许开始第一批；非最后批用户通过后允许开始原编排中的下一批。跨对话恢复时，先校验检查点中的规划、累计输出和批次批准，再定位首个未完成批次：实施中或已获修订指令的批次继续完成；非最后批待审阅时恢复摘要并等待用户；前批已通过时可进入下一批。最后一批已完成实施及验证记录时直接收尾，不继续等待旧审阅节点。`继续` 不批准待审阅批次，也不重置已经完成的工作。

## 批次执行

1. **实施。** 只启动当前批次中依赖已满足的任务。按委派收益门槛决定是否并行；共享接缝与集成由主 Agent 负责。持续登记实际持久化产品目标及必要实现补充；后续批次的写入不能提前开始。
2. **验证。** 回收本批全部任务并完成集成，按项目规则、实际改动风险及已批准门槛执行必要检查。本批交付前可在原授权范围内修复实现问题并复验；实质方案或产品边界变化仍须回退。无法在当前条件下解决的检查记录为 `failed` 或 `blocked`，说明原因、证据、影响与未覆盖范围，不把失败改记为通过。
3. **非最后批交付并停下。** 最后一批直接按下方完成规则收尾。其余批次保存对应 `I-*`、累计输出快照、验证结果及审阅指纹，将批次记为 `awaiting_review`，顶层记为 `awaiting_approval`。报告本批变更与可审阅路径、真实验证结果、偏差和遗留问题、下一批范围及续接位置。结束本轮实施等待用户，不预先派发后续写入，也不让尚在运行的写入任务越过暂停点。
4. **非最后批用户决定。** 用户明确通过本批且确认版本仍有效时记录批准；在同一任务只有一个清晰待审阅批次时，“通过”可批准它。有 `failed` 或 `blocked` 时，另需用户明确接受已披露的遗留问题，并记录接受说明；一般性通过不能代替这一决定，产品、安全或权限门槛也不能被其绕过。通过即允许进入下一批，无需再次询问是否启动；用户要求暂停时保存批准后停下。

非最后批审阅期间，用户明确要求修正当前批次时，转为 `revising`，在已授权范围内修正、验证后重新提交本批审阅。仅指出问题但未明确允许修改时，先说明处理建议；不以必要实现补充为由继续改动已提交审阅的版本。代码修正本身不要求重开实施文档批准；只有下文的实质变更才回退。

检查按 `passed`、`failed`、`blocked` 记录。用 Spec 与 Test 核对行为，不将每个 `T-*` 自动变成测试任务。不得删减已批准的必要验证，或用构建、模拟结果替代要求经过的真实边界。尚未完成的本批实现、失效授权和活动槽冲突不能作为验证问题跳过。不存在适用测试命令时，记录与实际风险相称的检查及其证据，不为填满字段新增测试设施。

后续批次可以按已批准方案继续修改前批涉及的文件；前批批准保留为当时版本的记录，不能据此宣称新版本已获用户审阅。后续交付须披露这些改动和受影响的验证。外部漂移或对已通过结果的实质返修，先核实影响，暂停相关批次及其下游，保留真实历史批准，不刷新指纹冒充新批准。

## 实施中的变更分级

仅在当前批次的实施或修订授权仍有效时应用以下分级。主 Agent 根据实际影响判断，不以是否新增文件或改动行数单独决定回退：

- **必要实现补充：** 为满足已批准契约或适用项目规则所必需的局部、可逆改动，例如补齐样式、资源或既有接口接线。必须能追溯到现有 `I-*` 及其契约或规则依据，不扩大产品范围、不新增库或模块依赖、不新增数据 owner、不改变模块边界、既有共享行为或外部契约，不引入新的实质风险，并有适当验证。不得突破明确的禁止目标、非目标或权限限制；实施文档中的命名文件清单本身不视为禁止必要配套文件。符合条件时继续当前批次，告知补充原因，记录实际路径、影响与验证，不重开文档批准或再次请求实施授权，也不能借此越过批次审阅。
- **实质技术方案变化：** 改变数据归属、模块依赖、共享机制、关键依赖顺序或验证策略等，已经超出原实施方案的保证。暂停受影响的写入及其下游工作，通常返回阶段 5；若问题来自更早的依据或业务场景，则返回相应阶段。
- **产品或权限边界变化：** 改变产品规则、外部契约、安全/隐私义务、不可逆操作或所需外部权限。暂停受影响的操作，回到最早负责该决定的阶段，取得明确确认。

后两类按[文档独立审阅与返修](document-review.md)取得受影响文档的修订授权，完成修订、重新审阅和一致性检查，并重新取得产品代码实施授权后，才能继续受影响的实施。当前批次内不依赖待决定事项且原授权仍有效的工作可以继续；无法隔离影响时扩大暂停范围。正式规划变更已使原授权失效时，不得继续以旧授权写入产品代码。

按关联改动的累计影响判定，不得拆小改动规避实质变更；证据不足以证明符合“必要实现补充”时，先核对其影响，仍无法界定才暂停相关部分。该分级不追认越权写入，也不覆盖待审阅时的停止要求。

必要实现补充只更新实施结果、当前批次与运行时写入范围，保留已批准文档和规划指纹。不要为追认实际文件清单改写 `implementation.md`，也不要把旧批准重新绑定到已改变的规划或审阅输出。

遵循仓库规则，保留用户无关改动。实施授权及必要补充不授权覆盖用户工作或执行额外的外部操作。除非用户另行要求，否则不要 commit、push、发布、迁移生产数据或执行其他外部变更。

## 最后一批与完成

最后一批完成时执行必要的整体集成与回归验证，并汇总所有已批准验证项的当前结果；不能只用最后一批局部检查替代前批遗留问题或跨批次验证。补齐完整变更清单、输出指纹、完成时间和真实验证结果，最后一批记为 `completed`，实施结果记为 `implemented`；只有验证全部通过才记为 `verified`。单批任务同样直接收尾。

前序批次均有有效用户批准、最后一批实施及必要验证记录完整时，校验检查点后自动将流程记为 `complete`，释放工作区活动槽并报告结果，不等待最后一批用户审阅或遗留问题接受，也不安排独立代码审阅。验证的 `failed`、`blocked` 及未覆盖范围如实报告，不阻止收尾；未完成的实施、失效授权、实质方案待决或活动槽冲突仍须先解决。

最终报告包含实际变更、真实验证结果及盲区、遗留问题及已有处置、方案偏差和完成状态；保留 `implemented` 与 `verified` 的区别。流程结束后的新修改按用户新指令处理，不自动延续已结束的写入授权。
