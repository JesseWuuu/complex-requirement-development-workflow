# 阶段 7：实施、验证与终结

仅在准备进入或恢复阶段 7、或处理实施偏差时读取。本文是实施变更分级与完成边界的详细规则；派发方式见[委派参考](subagent-delegation.md)。

获得明确的产品代码实施授权后，先校验三份文档和技术依据指纹仍与授权绑定输入一致。工作区模块还必须用自己的 owner 再执行一次活动槽 `check`；已经失去活动槽或另一个模块正在实施时，不得开始代码写入。

门禁通过后，按主 Skill 的职责分工与[委派参考](subagent-delegation.md)执行派发检查并依据已批准的 `implementation.md` 实施。文档包含实施编排时，从批准后的批次和实施包生成运行时任务；未包含时由主 Agent 按 `I-*` 串行实施。映射、降级和停止条件遵循委派参考。持续登记实际创建、修改、移动或删除的持久化产品目标，代码完成后执行下方验证与终结审阅；模块在审阅返回前保持 `in_progress`。

## 实施中的变更分级

仅在实施授权仍有效、且尚未派发终结代码审阅时应用以下分级。主 Agent 根据实际影响判断，不以是否新增文件或改动行数单独决定回退：

- **必要实现补充：** 为满足已批准契约或适用项目规则所必需的局部、可逆改动，例如补齐样式、资源或既有接口接线。必须能追溯到现有 `I-*` 及其契约或规则依据，不扩大产品范围、不新增库或模块依赖、不新增数据 owner、不改变模块边界、既有共享行为或外部契约，不引入新的实质风险，并有适当验证。不得突破明确的禁止目标、非目标或权限限制；实施文档中的命名文件清单本身不视为禁止必要配套文件。符合条件时直接继续阶段 7，告知补充原因，记录实际路径、影响与验证，不重开文档批准，也不再次请求实施授权。
- **实质技术方案变化：** 改变数据归属、模块依赖、共享机制、关键依赖顺序或验证策略等，已经超出原实施方案的保证。暂停受影响的写入及其下游工作，通常返回阶段 5；若问题来自更早的依据或业务场景，则返回相应阶段。
- **产品或权限边界变化：** 改变产品规则、外部契约、安全/隐私义务、不可逆操作或所需外部权限。暂停受影响的操作，回到最早负责该决定的阶段，取得明确确认。

后两类按[文档独立审阅与返修](document-review.md)取得受影响文档的修订授权，完成修订、重新审阅和一致性检查，并重新取得产品代码实施授权后，才能继续受影响的实施。不依赖待决定事项且原授权仍有效的工作可以继续；无法隔离影响时扩大暂停范围。正式规划变更已使原授权失效时，不得继续以旧授权写入产品代码。

按关联改动的累计影响判定，不得拆小改动规避实质变更；证据不足以证明符合“必要实现补充”时，先核对其影响，仍无法界定才暂停相关部分。该分级不追认越权写入，也不允许自动修复终结审阅发现。

必要实现补充只更新实施结果与运行时写入范围，保留已批准文档、规划指纹和审阅绑定；记录方式见[跨对话续接](cross-conversation-resumption.md)。不要为追认实际文件清单而改写 `implementation.md`，也不要把旧批准或审阅结论重新绑定到已改变的规划。

遵循仓库规则，保留用户无关改动。实施授权及必要补充不授权覆盖用户工作或执行额外的外部操作。除非用户另行要求，否则不要 commit、push、发布、迁移生产数据或执行其他外部变更。

## 验证与终结审阅

依据项目规则、实际改动风险及实施方案中已明确的检查选择必要验证；用 Spec 与 Test 的场景核对实现行为，不将每个 `T-*` 自动转换为待执行测试项。检查通过记为 `passed`；发现问题记为 `failed`；设备、账号、可控结果或其他条件不足而无法完成时记为 `blocked`，保留原因、证据和未覆盖范围。代码实施完成后的验证问题只记录，不自动修复、不为此重开文档或请求返修授权；继续其他可执行检查，不等待全部通过才启动代码审阅。不得删减已明确的验证要求，或用构建、模拟结果替代要求经过的真实边界。尚未完成的代码实施、失效的实施授权或工作区活动槽冲突仍按原门禁处理，不能冒充验证问题跳过。

代码完成后，记录完整变更清单、输出指纹和全部批准验证项的实际结果，实施结果记为 `implemented`；只有验证全部通过才记为 `verified`。两者都立即进入终结代码审阅，审阅范围、输入和返回格式按委派参考执行。主 Agent 不因审阅发现自动修改代码或文档、重开阶段或请求返修授权。

有效结论绑定当前规划、实施输出与验证结果后，无论有无发现，都先将模块标记为 `complete`，再执行工作区门禁的 `complete` 释放活动槽。最终报告包含变更路径、真实验证结果及其盲区、审阅发现、未解决问题和方案偏差；流程完成不代表验证全通过。审阅无完整结论时按委派参考恢复，后续修复仅在用户另行明确请求时作为新的工作处理。
