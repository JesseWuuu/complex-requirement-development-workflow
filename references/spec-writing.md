# Spec 写作指南

编写或修订 `spec.md` 时读取，包括表达与版式调整；成文门槛与返修处理遵循主 Skill。

## 核心审阅问题

要求的产品行为是否正确、完整且边界明确？

## 内容边界

Spec 正文负责产品语义。只包含：

- 问题、期望结果、范围、边界和重要的非目标；
- 关键规则、不变量、领域状态、状态转换和外部可观察行为；
- 会影响产品行为的逻辑数据或外部契约；
- 已确认决策、范围明确的非阻塞假设，以及决定受影响 UI 的 Figma 事实。

正文排除实施步骤、实施约束、仓库清单、无关日期、框架或分层选择、模块、文件、类、函数和技术方案。草稿可标明尚未解决的产品选择或证据缺口；存在阻塞项时不能标为可批准版本，按下方契约准入处理。返修记录按主 Skill 执行。

## 契约准入

产品规则统一按主 Skill 的“契约晋升门槛”纳入，本指南不另定义来源或例外。存在尚未解决的产品选择时，返回阶段 2 解决，不在 Spec 中替用户作决定。

## 追溯

仅对下游文档必须引用的关键规则使用 `R-*`。从属条件应保留在同一规则下。只有结论关键、存在争议或不明显时才添加来源指针。

## 规则表达与交付检查

按主 Skill 的[文档写作基线](../SKILL.md#文档写作基线)，用业务语言说明规则适用于谁、在什么条件下生效，以及用户会看到什么或可以做什么。状态名称首次出现时说明其业务含义；例外紧邻对应规则，不用“正常处理”“保持一致”代替具体结果。

例如，假设已确认的规则是刷新失败后保留列表：“失败保留旧态”应写成“刷新列表失败时，页面继续显示刷新前的列表内容。”这里的对象和结果不能靠读者猜测；提示文案、重试方式等未确认行为不随润色补入。

交付前检查是否能在不依赖讨论记录的情况下理解每条规则。仅当删除后仍能完整且清楚地表达原始需求、已确认决策和必须保留的既有外部行为时，才删除重复规则或解释。
